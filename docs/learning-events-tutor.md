# Учебные события и контекст помощника

Продолжение рекомендаций из `adaptive-recommendations.md`. Это решения реализации, а не эмпирически доказанные требования статьи. Формула, веса, пороги допуска и правила повторения не изменены.

## Журнал

`education.LearningEvent` дополняет существующие `TestAttempt`, `PracticeSubmission`, изменяемый прогресс и AI request logs. Он не копирует ответы, отчёты, документы, чаты, email, имена или ключи. Запись содержит время, владельца, модуль, материал, ссылки на попытку/сдачу и небольшой снимок факта:

| kind | Когда и что сохраняется |
| --- | --- |
| `material_completed` | Лекция впервые пересекла 95% в текущем цикле; процент и число модульных попыток. Повторные PATCH не создают завершения. После штатного сброса новое завершение — новое событие. |
| `practice_submitted` | Каждая реально сданная попытка практики, даже частичная: балл, источник оценки, завершённость и версия. Повтор того же submission не создаёт события. |
| `test_submitted` | Каждая новая попытка теста: версия, процент, `passed`; для adaptive — readiness, исторический threshold, `module_passed`, `module_completed`. FK `attempt` связывает событие с полной существующей записью попытки, модулем и учеником. |
| `module_reset` | Только реально выполненный адаптивный сброс; FK попытки, прежний прогресс материалов и ID снятых текущих сдач практик. Этот снимок не меняется после повторного обучения. |
| `module_unlocked` | Фактический переход модуля из locked в открытый после учебного действия. Ссылка на вызвавший его тест/практику/лекцию и исходный модуль. Не означает посещение страницы. |

События записываются в той же `transaction.atomic`, что и действие. Блокировка пользователя сериализует завершения, практики и оценивание/сброс; уникальные ключи предотвращают повторную запись одного факта. Ошибка записи откатывает всё действие. Проверки выполнены на SQLite; конкурентная работа PostgreSQL не проверялась. При сбросе порядок фактов — тест, сброс; при успехе — тест, открытие. Для восстановления порядка используйте ID по возрастанию (API возвращает новые первыми), время может совпадать.

Журнал фиксирует учебные действия, а не все изменения конфигурации: публикация, административное редактирование прогресса, смена доступа/порогов сами по себе не порождают события. Первое доступное состояние не считается открытием следующего модуля. Существующие данные не превращаются в придуманные события прошлого. Это не полный аудит действий администратора и не доказательство компетентности.

`GET /api/v1/learning-events/?page=1` — стандартная пагинация, только события владельца; параметр `user` у студента не расширяет область. Активный администратор видит все и может использовать `?user=<integer>`. Анонимный доступ запрещён. Ответ: `id,user,module,item,attempt,submission,kind,details,created_at`; числовые ссылки не дают доступа к чужим объектам. История собственных действий остаётся читаемой после отзыва доступа к курсу, как существующая история попыток. Запись/изменение/удаление через этот API отсутствуют. В `/django-admin/` есть просмотр с обычными Django permissions и фильтром kind; формы изменения, добавления и удаления отключены.

Фиксированный срок хранения не установлен. Автоматического удаления и переноса в очередь нет. FK защищены `PROTECT`, чтобы удаление связанной записи не разрушило причинную связь; обычное soft delete учебного контента сохраняется. Журнал не является защитой от ручного изменения БД привилегированным оператором.

## Повторная отправка теста

POST существующих `/items/{short_id}/attempts/` и `/lessons/{short_id}/attempts/` принимает дополнительный `request_id` (UUID). В пределах пользователя и теста повтор с тем же ключом и теми же answers возвращает ту же попытку (201), без обновления профиля, сброса и событий; это работает и сразу после неуспеха, когда подготовка уже сброшена. Другие ответы с использованным ключом — 400. Новая осознанная попытка использует новый UUID. Доступ и публикация проверяются и при повторе. Поле не выдаётся в ответе попытки.

Frontend сохраняет ключ и подпись отправленных ответов в sessionStorage рядом с черновиком; после потерянного ответа/перезагрузки повторяет его, после успеха удаляет. При изменении ответов создаёт новый ключ. Без sessionStorage ключ сохраняется в памяти до закрытия экрана. Для совместимости старый API без ключа работает как прежде: каждый POST означает новую попытку; сервер не может отличить сетевой дубль от сознательного повторения одинаковых ответов. Клиентам, которым нужна идемпотентность, необходимо передавать ключ.

## Контракт AI

Django сначала выполняет существующую `lesson_context` с проверкой доступа и публикации, затем `learning_context(user, material, course)`. Пользователь не может передать собственные оценки, course ID или контекст вместо серверного. Область — текущий материал/модуль доступного курса, только профиль текущего пользователя. Компетенции берутся из связей материала, при отсутствии связей — из опубликованного итогового теста модуля.

В `services/ai-tutor` POST `/api/chat` получает `learning_context` версии 1:

- `as_of`, `course_id`, `module_id`, `adaptive`;
- `current`: актуальные status, is_completed, threshold;
- `last_attempt`: последняя опубликованная в этом модуле попытка пользователя, ID, время, версия, процент, passed, readiness/threshold/module_passed/module_completed (null без adaptive). Это исторический факт, включая старый порог и накопленное завершение **на момент попытки**;
- до 12 текущих компетенций `{key,score}` по возрастанию показателя;
- до 5 рекомендаций первого этапа `{competency,item_id,title,reason}`. Используются сохранённые назначения только из последней попытки, только уместные компетенции и актуально разрешённые материалы того же модуля. Закрытые рекомендации не передаются даже текстом. Пустые данные остаются null/пустыми списками, старые попытки не дополняются придуманными рекомендациями.

AI-сервис проверяет версию, совпадение курса, типы/диапазоны/лимиты (весь контекст ≤12000 символов), заново формирует разрешённые поля и включает их в `buildResponsesInput`. Контекст принимается только с настроенным `API_SHARED_KEY`, совпадающим серверным ключом и без браузерного Origin; Django использует соответствующий `AI_SERVICE_API_KEY`. Невалидный контекст — 400, недоверенный — 403. Старые клиенты без контекста совместимы.

В системной инструкции отдельно закреплены историческое/текущее состояние и три результата. AI объясняет и помогает, но не меняет оценки, пороги или доступ и не обещает разблокировку. Названия/ключи/материал и сообщения пользователя — данные, не полномочия переопределить решения. Реальные ограничения продолжает применять Django; качество послушания живой модели этим тестом не доказывается. Ни запрос AI, ни его ответ не вызывают учебных переходов. Сбой тьютора возвращает существующую ошибку 503 и не мешает сдавать работу/тест.

Отдельные приватные avatar gateways используют серверный адаптер `learning_context_prompt` (≤12000 символов), созданный Django из того же контекста и правил. Оба шлюза включают его в system prompt перед материалом; собственные ключ/Origin-проверки шлюзов сохраняются. Это не поле, принимаемое от браузера Django. Контракт активного шлюза проверен с синтетическими потоками без AI/озвучки/NVIDIA. Сам NVIDIA runtime не проверялся.

Новый контекст не создаёт второй журнал запросов AI; существующая телеметрия и её политика остаются в AI-сервисе. Учебный журнал не содержит диалоги.

## Миграции и проверки

После завершения обоих этапов перед запуском нового кода выполнить штатный `migrate`: education `0020` (первый этап), assessments `0005_testattempt_request_id_and_more`, education `0021_learningevent`. Они добавляют поля/таблицу без исторического заполнения; обратный переход удаляет новые данные. Автоматический запуск миграций/деплой не выполнялся.

Содержательные проверки: `apps.education.test_events`, существующие adaptive/progress/recommendation tests, `apps.tutor`, `apps.activities.tests`; `node validation/learning-context.cjs` проверяет реальный обработчик `/api/chat` до prompt с заменёнными хранилищем, поиском и провайдером (не внешняя интеграция); `node --test services/avatar-gateway/gateway.test.cjs`; frontend tests/build, AI-service build. `e2e/adaptive.integration.e2e.ts` работает без API-перехвата на реальном локальном Django/временной SQLite: ru/en/kz, 1280/390, оба расхождения тест/модуль, повторный цикл, поздняя неудача, replay каждого теста, точный журнал. Фикстура `e2e/fixtures/adaptive_backend.py` не загружает production `.env`.

Это не проверка production/PostgreSQL, платного AI-провайдера или качества его ответов. Очередь, общий новый аналитический экран и политика автоматического удаления не добавлялись.

Проверено 2026-11-13 после объединения этапов: 182 backend-теста (181 успешно, один тест skip_locked требует PostgreSQL и пропущен); 248 frontend-тестов; обе сборки и типизация AI-сервиса; контракт learning-context и 7 тестов avatar gateway; 3 реальных интеграционных сценария Chrome на временной SQLite. Временные серверы остановлены. Это состояние незакоммиченных изменений в `feature/adaptive-support` обоих репозиториев, без push/merge/deploy.
